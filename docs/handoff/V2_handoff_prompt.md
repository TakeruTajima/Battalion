# 実装依頼：大隊指揮RTS 検証の道具 V2（作戦の探索）

## Git タグ

完了時に `proto-v2-planner` を打ち、push する。

## 背景

リポジトリ：`TakeruTajima/Battalion`（`proto-v1-objectives` まで完了）。

与えられた規則・地図・敵の下で、強い作戦を機械に探させる道具を作る。使い道は、規則と地図の検討と、開発側が意図した行動の検証。

**一番の注文は、開発側が想定していない攻略法を見つけること。** たとえば今の「塹壕を無視して村を取る」は、作戦の「型」（正面・片翼・両翼など）だけを検討していたら見つからない。そこで、探す手を型で縛らず、作戦の系統は結果から分ける。

- 仕様書：`docs/spec.md` の「検証の道具：作戦の探索（V1・V2。確定）」が正。特に「想定外を見つけるための作りの原則」と「限界」

## タスク

1. 道具：Unity の外で動く .NET のコンソールの道具（`tools/` の下）。複数のコアで並列に回せること。決まったシードで同じ結果を再現できること
   - **ゲームの規則はコピーしない**：Sim のソース（`Assets/Sim`）を参照して組み立て、パラメータは同じ `Assets/StreamingAssets/sim_params.json` と地図を読む。ゲームの規則や値を直せば、探索も自動でその規則で回ること。実験で値を変えるときは、ファイルを書き換えずに上書きの設定で渡す
2. 探す手（遺伝子）：プレイヤーが出せる命令そのもの
   - 青の4個中隊それぞれの会戦開始前の命令書（最大3段。各段の命令の種類、地図の地点、向き・攻める方角・範囲、拘束の距離、崩れたら、裁量、移る条件）
   - 信号弾3色の打ち上げの時刻（打たない、を含む）
   - 決まった時刻に伝令で送る追加の命令書（数本まで。判断枠と伝令の遅れは今どおり）
   - 型の遺伝子は作らない。今の通し実行の作戦は、初めの集団に混ぜる種にとどめる
3. 評価：候補ごとに数本のシードで回す（V1 の記録を使う）。目的は別々に扱う
   - 第一目標
   - 第二目標
   - 青の損害
   - 時間
4. 探し方：品質と多様性の探索（MAP-Elites など）を主にし、多目的の選び方を組み合わせる。系統の軸は、命令の中身ではなく会戦で起きたことから取る
   - 例：崩した赤の中隊の組み合わせ、青の通り道の広がりや向き、村を取った時刻
   - 系統の軸の選び方は設計で提案する
5. 期待との食い違い：開発側の期待を条件の一覧のファイルに書けるようにし、それに反する上位の作戦を報告する。初めの一覧は次の3つ
   - 「村を取った作戦は、塹壕の赤を崩している」
   - 「火力で抑えずに、開けた所を正面から陣地へ進む作戦は、大損害か失敗になる」（史実の目安）
   - 「陣地の射界の近く（100m 以内）を抑えずに横切る中隊は、大損害を受けるか前進が止まる」（史実の目安）
6. 出力
   - 系統ごとの上位の作戦の一覧（命令書の要約、目標の達成率、損害、時間。多くのシードで評価し直した値）
   - 期待との食い違いの一覧
   - 作戦の命令書のファイルへの書き出し
7. Unity での再生：書き出した作戦のファイルを読み込み、会戦開始前の命令書・信号弾・追加の命令書としてそのまま流して再生できる（メニューかキーで読み込む）
8. 実験の用意（回すのは Takeru。下の「長い計算」）
   - 両ステージで、多目的で探す回と、第一目標だけで探す回
   - 伝令の遅れをなくした版（全ての命令書が即座に届く）でも探し、遅れありと比べる（H4 が戦術に効いているか）
   - 規則の値を変えた版でも探せるようにする（`sim_params.json` の値を上書きする設定）。最初に比べたい候補は次の2つ
     - `terrain.moving_open_damage_mult`：1.0（今）／1.5／2.0（開けた所を動く中隊の被弾。P1b からの調整候補で、まだ 1.0 のまま）
     - `movement.turn_deg_per_sec`：6（今）／3／2（向き直りの速さ）

## テスト

- 単体テスト：
  - 同じシード・同じ設定で、探索の結果が同じになる
  - 書き出した作戦を読み込んで流すと、探索で評価したときと同じ結果になる（同じシードで）
  - 遺伝子から作る命令書が、プレイヤーの命令書の検査（P2b・P2b.1）を必ず通る（通らない遺伝子は直すか捨てる）
- 既存のテストは変わらない（Sim の規則は変えない）
- **長い計算は回さない**：Claude Code が回すのは、速いテストと、探索がひととおり動くことを確かめるごく短い試運転（数分）だけ。本番の探索（8 の実験）は Takeru がローカルで夜通し回す。回し方（コマンド、設定、所要の目安、出力の置き場所）を報告に書いて止まる。結果の読み解きは、出力を渡した後の依頼で行う

## 完了基準

- .NET の速いテストが全て通る。Unity で再生ができる（試運転で出た作戦で確かめる）
- 報告に、試運転の所要から見積もった本番の探索1回の所要時間と使うコア数、実験の回し方がある

## スコープ

- 含める：上のタスクのみ
- 含めない：赤の作戦の探索、会戦中に状況を見て判断を変える作戦、規則・地図の変更、勝率を目標の値に合わせる自動の調整
- 地図データとリファレンス実装は変更しない

## 方針

- **着手前に設計を短くまとめて報告し、返答があるまで実装に入らないこと。** 特に次を書く
  - 遺伝子の形と、変異・交叉の仕方
  - 系統の軸
  - 多目的の扱い
  - 評価のシードの本数と評価し直しの本数
  - 計算の予算（1回の探索の所要の見込み）
  - 作戦のファイルの形
  - Unity での再生の入り口
- 想定外を見つけることが一番の注文なので、型で縛っている箇所がないかを設計で自分で確かめ、あれば書く
- 完了したら止まって報告する
