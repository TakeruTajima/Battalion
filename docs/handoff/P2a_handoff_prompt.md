# 実装依頼：大隊指揮RTS プロトタイプ P2a（伝令）

## Git タグ

1. 着手前に、今の `main`（`proto-p1g.1-fix`）にタグ `proto-p1-map` を打って push する（P1 の完了）
2. P2a の完了時に `proto-p2a-runners` を打って push する

## 背景

リポジトリ：`TakeruTajima/Battalion`（`proto-p1g.1-fix` まで完了）。

P1 は人が遊んで問題なしと判断し、閉じる。ここから P2 に入る。P2 の目標は H4（命令の遅れが読み合いを生む）に触れることで、このゲームの一番の特徴にあたる。今は命令が即座に届くが、P2a から命令は伝令が運び、距離に応じて遅れて届く。伝令の数（判断枠）にも限りがあり、敵の射界を通る伝令は倒れることがある。

P2 は3段階に分ける：P2a 伝令（今回）、P2b 霧と報告、P2c 通信途絶と自律行動。

- 仕様書：`docs/spec.md` の「P2 詳細仕様」の「P2a：伝令（確定）」が正。あわせて「時間と命令系統」の節
- 霧（敵の姿が報告でしか分からない）は P2b。P2a では敵は今どおり全て見えている

## タスク

仕様の「P2a：伝令（確定）」を実装する。

1. 本部（青・赤）の位置と描画
2. 伝令の往復（準備30秒、秒速3m、中隊を追いかける、受領の報告で戻る）
3. 命令の受け渡し（届いてから練度の遅れの後に動き出す。届くまでは古い命令のまま。後から着いた命令が上書き）
4. 判断枠（3人まで。出せないときの表示）
5. 伝令の喪失（射界を通る間、毎秒0.3%）と、受領が来ないときの強制開放（往復予定の1.5倍）
6. 赤の予備隊の台本も赤の本部から伝令で届く
7. 表示：伝令の点と点線、「未着」の印と到着予定、上部バーの判断枠、出来事の欄、自動一時停止「受領報告なし」

パラメータ：新しい数値（本部の位置以外。伝令の速さ、準備時間、喪失の率、強制開放の倍率、判断枠の数）は `sim_params.json` に置く。キーを設計で提案する（仕様側で `sim_params.initial.json` に反映する）

## テスト

- 単体テスト：仕様の「検算」の3つ（600m で 230秒に届く、約 430秒で受領が戻り判断枠が空く、射界を 100秒通る伝令の生存率が約74%（多数回の試行で））。ほかに、届くまで古い命令が続く、後着の命令が上書きする、判断枠が3で止まる、受領が来なければ1.5倍で枠が空く、動く中隊を伝令が追いかける、一時停止中の命令も同じ遅延で届く
- S1〜S6 は命令のない場面なので変わらない見込み。±15% 以内であることを確かめる
- 通し実行の表を P1g.1 と並べて報告する。作戦の命令は全て伝令で届くようになるので、結果は変わる。回帰の指標として扱い、作り込みはしない

## 完了基準

- Unity 6.3 LTS（6000.3.11f1）と .NET でテストが全て通る
- 通し実行の表と、大きく変わった作戦の理由が報告にある
- `Sim` が UnityEngine を参照しない
- 報告に、人が触って確かめる項目の一覧と、変わった操作の早見表を含める

## スコープ

- 含める：上のタスクのみ
- 含めない：霧と報告（P2b）、通信途絶と自律行動（P2c）、伝令の経路探索、本部の移動、砲兵（P3）以降
- 地図データとリファレンス実装は変更しない

## 方針

- **着手前に設計を短くまとめて報告し、返答があるまで実装に入らないこと。** 特に、命令の状態の持ち方（発令・移動中・受領・開始待ち・実行中）、伝令と P1e の命令の下見・P1d の追撃の許可などとの関係、射界の判定に使う地図（どの陣営の露出の地図をどう使うか）、通し実行の作戦の命令をどう伝令に載せるか、パラメータのキーを書く
- 仕様の解釈で迷ったら一覧に残し、もっとも素直な解釈を提案に含める
- Unity は 6.3 LTS（6000.3.11f1）で開く
- 完了したら止まって報告する。P2b には進まない
