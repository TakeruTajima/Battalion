# 実装依頼：大隊指揮RTS プロトタイプ R2（陣地の守りの向き）

## Git タグ

完了時に `proto-r2-fortification` を打ち、push する。

## 背景

リポジトリ：`TakeruTajima/Battalion`（`proto-r1-suppression` まで完了）。

戦術の目録（`docs/design/tactics.md`）を作り、史実の戦術が Sim で効くかを、戦術がつけ込む因果ごとに確かめた。一番の穴は、塹壕・陣地構築・浅い掩体の守りが、どの向きから撃たれても同じに効いていること。そのため塹壕の中隊を側面から撃っても、正面から撃つのに比べて損害は 1.5倍、士気の減りは 3倍にとどまる。

史実では、塹壕は軸に沿った射撃（縦射）をほとんど防げない。守りが正面だけに効けば、損害は 5倍、士気の減りは 10倍になる。「側面を突いたのに通らない」と感じさせないために、守りに向きを持たせる。

- 仕様書：`docs/spec.md` の「R2：陣地の守りの向き（確定）」が正。背景は `docs/design/tactics.md` の「4. 見つかった穴」

## タスク

1. 陣地の向き
   - 地図の塹壕：シナリオの定義で与える（シナリオA は、会戦開始時にその塹壕にいる中隊の向き。地図ファイルは変えない）
   - 陣地構築：完成したときの中隊の向き
   - 浅い掩体：掘り始めたときの中隊の向き
   - 後から変わらない。奪った塹壕は、攻め手には逆向き
2. 守りの効き方：撃ってきた敵が、陣地の向きの正面の弧（±60°）にいるときだけ効かせる。外なら、守りの倍率を `terrain.fortification_off_arc_mult`（1.0）に置き換える。村・森などの向きのない守りは今のまま
3. 検証の場面 S10・S11 と、期待を判定するテスト
4. 表示：中隊の詳しい表示に、陣地の向きと「今受けている射撃に陣地が効いているか」を出す。地図に陣地の向きを示す小さな印（塹壕の正面側の線など）

パラメータ：`terrain.fortification_off_arc_mult` を `sim_params.json` に足す。仕様側で `sim_params.initial.json` に反映するまで、同一性のテストは落ちてよい

## テスト

- 単体テスト：
  - 正面の弧から撃たれると守りが効き、側面・背面から撃たれると効かない
  - 中隊が向きを変えても、陣地の向きは変わらない
  - 陣地構築・浅い掩体の向きが、完成・掘り始めの向きになる
  - 村・森の守りは向きによらない
  - 奪った塹壕は、奪った側にとって逆向き（もとの向きの正面の弧から撃たれたときだけ守られる）
- S10・S11 の期待を満たす。満たさなければ、値を変えずに結果と理由を報告して止まる
- S1〜S9 が変わらないこと（変わる場合は理由）
- **速いテストは .NET と Unity（バッチモード）の両方を Claude Code が回す**。シナリオA の通し実行は Takeru がローカルで回すので、回し方と、V1・R1 の値と比べるところを報告に書く

## 完了基準

- .NET と Unity の速いテストが通る（`SimParamsIsIdenticalToInitial` は反映待ちで落ちてよい）
- 報告に、S10・S11 の結果、S1〜S9 への影響、通し実行の回し方、人が触って確かめる項目がある

## スコープ

- 含める：上のタスクのみ
- 含めない：正面の弧の外を撃つ ×0.5 の見直し、向き直りの速さ、奪った直後の弱さ、障害物、P2d、P4
- 地図データとリファレンス実装は変更しない

## 方針

- 規則は仕様に書いてあるので、**着手前の設計報告は不要**。迷った点と自分で決めた点は報告に一覧で残す（特に、シナリオA の塹壕の向きの決め方、陣地構築の途中で向きを変えた場合）
- 返事と報告は日本語で書く
- 完了したら止まって報告する
