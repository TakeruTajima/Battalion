# 実装依頼：大隊指揮RTS 検証の道具 V1（作戦目標による評価）

## Git タグ

完了時に `proto-v1-objectives` を打ち、push する。

## 背景

リポジトリ：`TakeruTajima/Battalion`（`proto-p2c2-requests` まで完了）。

次に、作戦を機械に探させる道具（V2）を作る。与えられた規則・地図・敵の下で強い作戦を探し、規則と地図の検討や、開発側が意図した行動の検証に使う。一番の注文は、開発側が想定していない攻略法（例：塹壕を無視して村を取る）を見つけること。

その前提として、会戦の結果を「勝ち負け1つ」ではなく作戦目標ごとに評価し、何が起きたかを記録できるようにする。V1 はその土台。

- 仕様書：`docs/spec.md` の「検証の道具：作戦の探索（V1・V2。確定）」の V1 が正。あわせて「作戦目標（記録のみ。評価は V1 で入れる）」

## タスク

0. **先に：Unity と .NET の結果のずれを調べる**
   - P2c.2 の報告の「注意」にある件。ステージ2 の段階つき（シード1）のログが、Unity と .NET で違った
   - P2c.1.2 までは、同じハッシュのテストが Unity でも通っていた。そのため「計算の違い」で片付けず、P2c.2 の変更（伝令の動きの共通化など）で Unity でだけ結果が変わる計算が入った可能性を疑う
   - 両方でログを出し、最初にずれた行を特定して、原因を報告する。直し方の案も添える
   - 直すのは報告の後（ここで一度止まる）。V2 では「探索で見つけた作戦を Unity で再生すると同じ結果になる」が前提なので、ずれを残したまま先へ進まない
   - このタスクの報告で一度止まり、返答の後に 1 以下へ進む

1. 作戦目標の判定
   - 青の第一目標：村の奪取（今の勝ちの条件）
   - 青の第二目標：塹壕の敵の排除（塹壕に配置した赤の中隊が、90分の時点で全て指揮下にない、または盤上にいない）
   - 赤の目標：村の死守
   - どの赤の中隊が「塹壕に配置した中隊」かは、シナリオの定義（`MapScenario`）に持たせる
2. 会戦の結果の記録（Sim の読み取りの口と、機械が読める形の出力。JSON など）
   - 目標ごとの達成
   - 両軍の損害
   - 村を取った時刻（初めて第一目標の条件を満たした時刻と、90分の時点の判定）
   - 崩れた・降伏した・離脱した中隊と時刻
   - 撃ち合った組（どの青がどの赤を、いつからいつまで、どれだけ撃ったか）
   - 青の各中隊の通り道（30秒ごとの位置）
3. 通し実行の表に、目標ごとの達成率（第一・第二・両方）を足す
   - 作戦を1つ足す：「全中隊に村の中心への前進だけを命じる」（素直な作戦の基準。P2c.1.2 のプレイで「これだけでまぁ勝てる」と分かったため）
4. Unity の会戦の終わりの画面に、目標ごとの達成を出す（「第一目標：達成　第二目標：未達成」）

## テスト

- 単体テスト：
  - 塹壕の赤を崩さずに村を取った場合、第一目標だけ達成になる
  - 塹壕の赤を全て崩して村を取った場合、両方達成になる
  - 記録の撃ち合った組と通り道が、実際の会戦と合う（小さな場面で確かめる）
- 会戦の規則は変えないので、通し実行のログ（決定性のハッシュ）は P2c.2 と一致するはず（記録を足すことでログが変わるなら、ログに出さず読み取りの口だけにする）
- **長い計算は回さない**：Claude Code が回すのは速いテスト（単体テストと、短い確かめ）だけ。通し実行（ハッシュの一致と、目標ごとの達成率つきの表）は Takeru がローカルで回すので、回し方（コマンドと所要の目安）を報告に書いて止まる。結果は次の依頼で渡す

## 完了基準

- .NET の速いテストが全て通る。Unity でコンパイルが通る
- 報告に、記録の形の一覧と、通し実行の回し方がある（通し実行の結果は Takeru が回して確かめる）

## スコープ

- 含める：上のタスクのみ
- 含めない：作戦の探索（V2）、赤の振る舞いの変更（P4）、シナリオB
- 地図データとリファレンス実装は変更しない

## 方針

- 返事と報告は日本語で書く

- 規則は仕様に書いてあるので、**着手前の設計報告は不要**。記録の形（項目と型）は報告に一覧で書く。V2 がそのまま使う
- 完了したら止まって報告する。V2 には進まない
