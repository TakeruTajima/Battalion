# V1 タスク0 報告：Unity と .NET の結果のずれ

依頼文 V1 のタスク0。P2c.2 の報告の「注意」にあった、ステージ2 の段階つき（シード1）のログが Unity と .NET で違った件を調べた。直すのは返答の後。

## 結論

- **会戦の計算は Unity と .NET で全く同じ**。ずれは、ログに数を書く所（`JsonLineBuilder` の数の書き方）だけ。Unity（Mono）の `double.ToString("R")` が、.NET と同じビット列の値を 17桁で書くことがある
- **P2c.2 の変更が原因ではない**。P2c.1.2 のタグの版でも、Unity と .NET で同じ2行が同じように違う
- 調べる中で、もう1つ見つけた：**Unity（Mono）の `double.Parse` は、正しく丸めないことがある**（1ビット違う値を返す）。今の `sim_params.json`・地図・参照の結果の数は全て両方で同じに読めているので、今の会戦には効いていない。ただ、値を足したり変えたりすると、Unity でだけ会戦の入力が1ビット違う恐れがある

## 調べたこと

### 1. ずれた行（P2c.2 の版、ステージ2 の段階つき、シード1、90分）

両方でログを全て書き出して比べた。3929行のうち、違うのは2行だけ。どちらも 10秒ごとの位置の記録（`unit_snapshot`）の数の書き方。

| 行 | 項目 | .NET | Unity |
| --- | --- | --- | --- |
| 1164（t=1620 の R3） | x | `1712.764049` | `1712.7640490000001` |
| 2029（t=2790 の B4） | y | `1284.064166` | `1284.0641659999999` |

兵力・士気・時刻・ほかの位置、その後の全ての行は同じ。会戦の進み方は同じで、数の書き方だけが違う。

### 2. 値そのものは同じ

その2つの値を、元の値・丸めた値ともにビット列で比べた。

| 値 | 元の値 | 小数第6位で丸めた値（`Math.Round(v, 6)`） | .NET の `"R"` | Unity の `"R"` |
| --- | --- | --- | --- | --- |
| t=1620 の R3 の x | `1712.764048901362` `409AC30E62D5CF94`（両方同じ） | `409AC30E62DC6E2B`（両方同じ） | `1712.764049` | `1712.7640490000001` |
| t=2790 の B4 の y | `1284.0641658391014` `40941041B4B091D8`（両方同じ） | `40941041B4BB5E0F`（両方同じ） | `1284.064166` | `1284.0641659999999` |

- 元の値も丸めた値もビット列まで同じ。違うのは `ToString("R")` の出す文字だけ
- 定数 `1712.764049` をそのまま `"R"` で書いても、Unity は `1712.7640490000001` と書く（15桁の `"G15"` なら両方 `1712.764049`）。Mono の `"R"` は、15桁で書けば往復できる値でも 17桁を選ぶことがある
- ログの数は全て `Json.cs` の `AppendNumber`（小数第6位で丸めてから `"R"`）を通る。`"R"` を使っているのはここだけ

### 3. P2c.1.2 の版でも同じ

P2c.1.2 のタグ（`proto-p2c.1.2-fix`）を別の作業ツリーに取り出し、同じ場面のログを Unity と .NET で書き出した。

- P2c.1.2 の版でも、Unity と .NET で同じ2行が同じように違う（行・項目・文字まで同じ）
- P2c.2 の版のログから中隊の伝令の行を除くと、Unity でも .NET でも、P2c.1.2 の版のログと1バイトも違わない

P2c.2 の変更は Unity でだけ結果が変わる計算を入れていない。前からあったずれが、P2c.2 で初めて見えた。

**「P2c.1.2 までは Unity でも通っていた」について**：Unity と .NET で同じハッシュを確かめていたのは、決定性のテスト（`FlatMapLogMatchesP02`：平地の S1・S3・S4・S6・接近戦の5通り）だけ。シナリオA のログのハッシュ（`ScenarioLogHashTests`）は、ハッシュを出すだけで、何とも比べていなかった。平地の5通りのログには、たまたま Mono の `"R"` が 17桁を選ぶ値が出ていない。シナリオA のハッシュを Unity で .NET の値と比べたのは、P2c.2 の `CouriersDoNotChangeTheBattle`（初めの版）が最初。

### 4. 数の読み方（`double.Parse`）も Unity では正しく丸めないことがある

| 文字 | .NET | Unity |
| --- | --- | --- |
| `1712.764049` | `409AC30E62DC6E2B` | `409AC30E62DC6E2B` |
| `1284.064166` | `40941041B4BB5E0F`（正しい） | `40941041B4BB5E10`（1ビット大きい） |
| `0.1`・`0.003`・`1.3`・`2.7182818284590451` | 同じ | 同じ |

- JSON の数は `Json.cs` の `ParseNumber`（`double.TryParse`）で読む
- 今のファイルの数は、全て両方で同じビット列に読めた：`sim_params.json` 203個、`scenario_a1.json`・`scenario_a2.json` 各 2469個、`reference_results.json` 83個（ビット列をつないだハッシュが一致）
- 今は会戦に効いていない。だが、これから足す値・変える値・V2 の探索で書き出して読み戻す作戦（地点の座標など）が、Unity でだけ1ビット違って読まれうる。V2 の前提（探索で見つけた作戦を Unity で再生すると同じ結果）を崩しうる

## 直し方の案

### 案A：ログの数の書き方を、実行環境によらない形にする（ずれの直し）

`AppendNumber` の `Math.Round(v, 6)` と `"R"` を、整数を使った書き方に置き換える。

- `m = Math.Round(v × 1,000,000, 0から遠い方へ)` を整数（long）にし、「整数部.小数部（末尾の 0 を落とす）」で書く。例：`1712764049` → `1712.764049`
- .NET の今の `Math.Round(v, 6)` も中では「×1,000,000 して丸めて ÷1,000,000」なので、選ばれる数字は同じ。.NET の `"R"` が書く文字とも同じになる（0.0001 以上 10億未満。ログの数は全てこの範囲）
- 0.0001 未満の小さな数（例：0.000012）は、.NET の `"R"` が `1.2E-05` と書くので、同じ形で書く
- **.NET のログは1文字も変わらない**（P0.2 からの決定性のハッシュ、P2c.1.2・P2c.2 のハッシュはそのまま使える）。Unity のログが .NET と同じになる
- 確かめ：.NET の速いテスト（決定性のハッシュを含む）が通ること。Takeru のローカルで `CombatLogMatchesP2c12`（36通り）が一致すること。Unity でステージ2 の段階つき（シード1）のログが .NET と1バイトも違わないこと

### 案B：JSON の数の読み方を、実行環境によらない形にする（読み方の直し）

`ParseNumber` を、正しく丸める読み方に置き換える。

- 有効数字 15桁以下で、10 の指数が ±22 以内の数（今のファイルの数は全てこれ）は、「整数 × 10ⁿ」または「整数 ÷ 10ⁿ」の1回の掛け算・割り算で読む。これは正しく丸まることが知られている（両方とも整数と 10ⁿ が double で正確に表せるため）。Unity でも .NET でも同じビット列になる
- それ以外の数は、今どおり `double.Parse` に任せる（地図や設定には現れない）
- .NET では、今のファイルの数の読み方は変わらない（.NET の `double.Parse` は正しく丸めるので、同じビット列）

### 案C：Unity と .NET のずれを見張るテストを足す

- 速いテスト：シナリオA の作戦の短い会戦（例：ステージ2 の段階つき、シード1、90分。約5秒）のログのハッシュを、.NET で取った値と比べる。Unity でも同じテストが通ることで、ずれを自動で見つけられる
- 速いテスト：`sim_params.json`・地図・参照の結果の数を全て読み、ビット列をつないだハッシュを .NET で取った値と比べる（読み方のずれを見張る）

**提案**：A・B・C を全て入れてから、タスク1 に進む。A でログのずれがなくなり、B で入力のずれの芽を摘み、C でこの先のずれを Unity のテストで見つけられる。A と B は .NET の結果を1ビットも変えないので、通し実行の表は P2c.2 のまま（.NET の速いテストで確かめ、ハッシュの一致は Takeru のローカルで確かめる）。

## 迷った点

1. **A の範囲**：0.0001 未満と 10億以上の数の書き方は、.NET の `"R"` の形（`1.2E-05` など）に合わせる。今のログに 10億以上の数は出ないので、そこは今どおり `"R"` に任せる案もある（出ないことをテストで確かめる）
2. **B の範囲**：JSON の読み方だけを直す。Sim の中で `double.Parse` を使っているのは `Json.cs` だけ（表示・テストの側も、数は `JsonValue` で読む）
3. **Unity の他の計算**：今回の2つ（数の書き方・読み方）以外に、Unity と .NET で結果が変わる計算（`Math.Sin` など）は見つかっていない。会戦の計算が 90分まで全て同じビット列だったことから、少なくとも今の作戦の範囲では同じと読む。C のテストで見張る

## 直した結果（返答の後。A・B・C を全て入れた。迷った点 1〜3 は提案どおり）

- **A**：`Json.cs` に `JsonNumber.Append` を足し、ログの数を整数から書くようにした。0.0001 未満は .NET の `"R"` と同じ `1.2E-05` の形。10億以上は今どおり `"R"`
- **B**：`JsonNumber.TryParse`（正しく丸める読み方。読めない数だけ `double.Parse` に任せ、その数を `FallbackCount` に数える）。JSON の数は全てこれで読む
- **C**：`CrossPlatformTests`（28件）
  - ログの数の書き方（14通り。Mono の `"R"` が 17桁で書いた2つの値を含む）
  - .NET では、新しい書き方が今までの書き方（`Math.Round(v, 6)` と `"R"`）と同じ文字になる（乱数で作った 20万個。Unity では飛ばす）
  - JSON の数の読み方（7通り。Mono が 1ビット大きく読んだ `1284.064166` を含む）
  - 設定（`sim_params.json`・`sim_params.initial.json`）・地図2つ・参照の結果の数が、全て正しく丸める読み方で読める
  - シナリオA の作戦（ステージ2 の段階つき、シード1、90分）のログ全体のハッシュが、直す前に .NET で取った値と同じ
- **確かめたこと**
  - .NET：速いテスト 277件と見張りのテスト 28件が全て通過。決定性のハッシュ（P0.2 からの値）も、ステージ2 の段階つきのログも、直す前と1バイトも違わない（.NET のログは変わらない）
  - Unity 6.3：速いテスト 315件中 314件通過、失敗 0件（飛ばした1件は上の .NET だけの比べ）。ステージ2 の段階つきのログのハッシュが .NET と同じになった
